# 00 - Operating Model

## 目标

把“知道怎么操作”转化为“任何运营人员都能稳定执行，并能判断何时停止”的流程。

## 三个闭环

### A. 商品准备闭环

`选品 -> 商品卡 -> 核价 -> SKU -> 素材 -> 合规 -> 上架`

该闭环解决“做什么、卖多少钱、怎么表达、能不能发”。

### B. 履约闭环

`订单 -> ERP 推单 -> 面单 -> 发货 -> 轨迹 -> 异常处理`

该闭环解决“卖出后能否按时、正确地交付”。

### C. 运营反馈闭环

`活动/流量/广告/售后 -> 诊断 -> 只修改问题环节 -> 复测`

该闭环解决“为什么不增长、为什么亏钱、下一轮只改什么”。

## 角色边界

| 角色 | 主要责任 | 关键审批 |
| --- | --- | --- |
| 商品负责人 | 选品、供应商、规格和成本 | G0 选品通过 |
| 价格负责人 | 核价表、利润底线、SKU 角色 | G1 价格通过 |
| 内容/设计 | 图片、标题、卖点和素材授权 | G2 素材通过 |
| 合规负责人 | 税务、主体、标签、禁限售和敏感表述 | G3 合规通过 |
| 上架运营 | 模板、商品字段、批量发布和结果核对 | G4 发布通过 |
| 履约运营 | ERP、订单、面单、库存和异常单 | G5 履约通过 |
| 广告/运营 | 活动、流量、广告和复测 | G6 增长复测 |
| 售后 | 退款、差评和问题回流 | G7 售后闭环 |

同一人可以承担多个角色，但审批记录不能省略。

## 工作单元

所有流程以 `product_brief_id` 为追踪主键。一个商品从创建到归档只能有一份当前有效商品卡；历史版本只追加，不覆盖。

任务运行时另生成 `run_id`，用于关联该次素材、上架、推单和异常记录。

## 设计边界

- SOP 负责人工执行步骤、业务规则和验收标准。
- Agent 负责解析、归纳、生成建议和发现冲突。
- 脚本负责成本、价格、数量、字符数和状态校验。
- 浏览器扩展或 RPA 负责确定性点击，但必须支持暂停、幂等和结果查询。
